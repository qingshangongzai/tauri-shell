# Code Review

> 编码规则（技术栈、目录、核心原则、前端/Rust/安装器规范、行尾契约、测试约定等）以根目录《开发规范.md》为唯一真源；本 skill 只负责审查流程与产出格式，规则细节见《开发规范.md》，冲突时以它为准。

只读模式：只分析问题、给出结论，**不修改任何代码**。但允许（且建议）运行只读的验证命令——`cargo check`（src-tauri/ 下）、`cargo test`（src-tauri/ 下）——用退出码与实际输出锚定"通过 / 失败 / 编译错误"等事实性结论，不要凭推断断言。验证托盘契约时可运行 `npm run test:tray`（该脚本会临时改写 `dist/index.html` 与 `dist-min/` 后自动还原，非纯只读）。

**实证原则（对抗幻觉）**：审查涉及第三方 crate / Tauri 内部 API 的签名或运行时行为（如 `data-tauri-drag-region` 的点击判定、`apply_window_chrome` 的注入时机、`plugin:window|*` 命令名）时，读实际源码（`~/.cargo/registry`、`node_modules/`）或官方文档验证，禁止凭记忆断言——框架版本差异大，记忆极易过时（例：Tauri v2 的拖拽由注入的 drag.js 判定，`BUTTON` 等可点击元素自动阻止拖拽，`-webkit-app-region` 不生效，与 v1 不同）。框架内部行为无法从项目代码直接看出时，标注"据经验，未验证"或补一次源码确认。

## 审查流程

0. **排除 Git 忽略的文件**：被 `.gitignore` 忽略的文件（如 `.zcode/`、`.qoder/`、`待优化清单.md`、`dist-min/`、`app-bundle.zip` 等）不属于审查范围，即使对话中修改过，也**一律不审查、不出现在审查结果中**。若本次改动全部属于被忽略文件，直接告知用户"改动均为 Git 忽略文件，不在审查范围内"。不确定某文件是否被忽略时，用 `git check-ignore <路径>` 验证。
1. **按变更复杂度分流**（与 commit-message-generator 的"简单/复杂修改"分流对齐）：
   - **简单变更（快速通道）**：纯样式数值调整（圆角/间距/尺寸/令牌颜色）、注释、重命名等无逻辑改动的变更，且对话上下文已完整覆盖改动内容与意图（如改动由本轮对话产生）时，跳过步骤 2-5，**不执行任何 git 命令**，直接基于对话上下文审查；维度精简为「规范合规」（令牌/硬编码数值，见《开发规范.md》第 4 节）、「无效修改」、关联一致性（共享设计令牌三处同步、Rust 参数与前端调用一致性，见《开发规范.md》第 3 节）；对存疑点直接 Read 源文件核实后再下结论
   - **复杂变更（完整流程）**：涉及新逻辑、重构、新增文件、跨模块联动（含托盘契约三处联动），或对话上下文不足以确信完整覆盖改动时，执行步骤 2-5
2. 执行 `git -c core.quotepath=false diff HEAD --no-color --output=.git-diff.txt`，将暂存+未暂存的所有变更输出到项目根目录的临时 txt 文件（`--output` 由 git 直接写文件，绕过 shell 管道/重定向，避免行尾截断与编码损坏——PowerShell 下**禁止用 `>` 重定向替代**，会写成 UTF-16；`--no-color` 去除 ANSI 转义码；`-c core.quotepath=false` 防止中文路径被转义成八进制序列；`git diff HEAD` 一条命令覆盖暂存与未暂存两种状态）。用户指定文件则直接读全量
3. 执行 `git -c core.quotepath=false ls-files --others --exclude-standard` 列出未跟踪的新文件（输出量小，直接读终端输出即可，无需落盘）——`git diff HEAD` **不含 untracked 文件**，会漏审新建的页面/脚本/组件；对列出的每个文件用 Read 工具读取全量内容一并审查
4. 使用 Read 工具读取 `.git-diff.txt`，获取已跟踪文件的变更；阅读变更区域前后各 20 行上下文，理解改动意图；**报告行号时以 `@@` 段头标注的起始行为基准换算回源文件真实行号**，不要直接使用 diff 内的相对位置；对将写入报告的 🔴/🟡 项，落报告前回读源文件对应区域确认真实行号（`@@` 换算本身易错，行号作为修复依据时尤须确认）
5. 生成审查结果后，删除 `.git-diff.txt`（已在 `.gitignore` 中；若上次审查中断残留，本次开始前先清理）
6. 按下方维度审查，判定标准读《开发规范.md》对应节
7. 仅输出有问题项，全通过输出"✅ 未发现问题"

## 审查维度

> 🔴 必须修复 | 🟡 建议优化。每维度的判定标准以《开发规范.md》为准，下表只标"看什么"与出处。

| # | 维度 | 看什么 | 出处 |
|---|------|--------|------|
| 1 | 过度设计 🔴 | 当前不需要的抽象/复杂度 | 核心原则第 1 条 |
| 2 | 冗余代码 🔴 | 定义了但未使用的代码 | 核心原则第 2 条 |
| 3 | 无效修改 🟡 | 不产生实际效果的改动 | 核心原则第 3 条 |
| 4 | 复杂逻辑 🟡 | 可读性差或过度复杂 | 核心原则第 4 条 |
| 5 | 过度防御 🟡 | 针对"不可能发生"场景的防御 | 核心原则第 5 条 |
| 6 | 命名清晰 🟡 | 名称表达意图、风格与既有命名一致 | 核心原则第 6 条 |
| 7 | 规范合规 🔴 | 令牌取色 / 去线留白 / 响应式 / 单文件资源 / 无障碍 / 窗口交互 / 托盘契约 / 范围克制（8 项对照表） | 「前端规范」节 |
| 8 | Rust 规范 🔴 | 命令注册遗漏（`generate_handler!` 列表）、snake_case 命名、托盘契约三处一致 | 「Rust 后端规范」节 |
| 9 | 测试完整性 🔴 | 逻辑层改动是否按门禁跑 `cargo test` / `npm run test:tray` | 「测试」节 |

## 审查范围

覆盖被改动的 `dist/index.html`、`dist/tray-menu.html`、`components/`、`scripts/`、`src-tauri/` 与 `installer/`。Rust 代码（两处 `src-tauri/`）只检查明显的逻辑错误、命令注册遗漏（`generate_handler!` 列表）、命名规范与托盘契约，不深入审查所有权和生命周期。

## 输出格式

| # | 文件:行号 | 严重度 | 维度 | 问题描述 |
|---|----------|--------|------|---------|
| 1 | dist/index.html:1420 | 🔴 | 冗余代码 | CSS 变量 `--foo` 定义后未被引用 |
| 2 | dist/index.html:2200 | 🟡 | 复杂逻辑 | `handleSave` 超过 80 行，建议拆分校验与存储逻辑 |

- 每项附 1-2 句修复建议
- 🔴 必须修复项排在前面，🟡 建议优化项排在后面
- 若某维度无问题，不输出该维度
