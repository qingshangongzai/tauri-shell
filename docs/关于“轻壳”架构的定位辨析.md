# 关于“轻壳”架构的定位辨析

> “轻壳”——基于 Tauri 将纯 HTML 页面打包为 Windows 桌面应用的做法。
> 本文回答“为什么用、什么时候不该用轻壳”，[使用说明.md](./使用说明.md) 回答“怎么用”，两者配合阅读。

先说结论，不绕弯：**“轻壳”确有鸡肋的一面，它的应用场景本身就非常局限。** 大多数项目用不到它，用到了也常常是“花了桌面端的代价，没得到桌面端的好处”。但鸡肋不等于无用——它是**特化品**而非**替代品**：适用面窄，可一旦命中少数几个“非桌面形态不可”的需求，Web 方向给不了。本文按“局限在哪里 → 什么场景非它不可 → 怎么判断 → 本项目对照”的顺序辨析。

---

## 一、 鸡肋是事实：轻壳的应用场景天然很窄

“轻壳”的“两头不讨好”是有道理的：论功能上限，它接不住后端；论轻便，它比不过一个网页。三条边界划下来，适用面已经很窄。

### 1. 有后端依赖的项目：直接出局

对于大多数成熟的应用，核心价值往往依赖后端服务（Python、Java、Go 等）。

* **现实困境**：Tauri 的原生后端是 Rust，无法直接封装现有的非 Rust 后端。
* **重构代价**：强行“套壳”意味着把后端逻辑用 Rust 重写——不是加个壳，是换掉整个底层。这在工程上是巨大成本，更是技术栈的彻底更迭。
* **结论**：**带后端的项目，轻壳不适用，这不是妥协能解决的。**

> **本项目对应**：轻壳主动承认并利用这条边界——Rust 层几乎零逻辑，仅 `get_file_size`（拖放示例）、
> `apply_window_chrome`（自动边框）与托盘相关三个命令；业务逻辑全部留在前端 HTML。
> 它只解决“把 HTML 变成 Windows 软件”这一件事，不提供、也不承诺任何后端能力。

### 2. 纯前端小工具：与网页功能重叠，代价却更高

对于逻辑简单的纯前端工具，轻壳能提供的功能（运行 HTML）与 Web 方向完全重叠，构建门槛却高得多。

* **Web 方向（PWA/裸 HTML）**：零构建、即时可用、链接即分发，浏览器自带信任体系。
* **轻壳方向**：要编译、要构建，产物体积从几 KB 膨胀到数 MB。
* **现实**：如果只是自用或内部分发的工具，这些额外代价换不来任何功能提升——**此时轻壳就是鸡肋。**

> **本项目对应**：环境成本可用[云构建](./使用说明.md#云构建github-actions)（GitHub Actions）转移——本地零环境，
> fork 后网页上改 HTML、打 tag 即得安装包；页面本身浏览器双击即可调试。但这只是把代价“搬走”，并没有消除：
> 每一次改版仍要重新构建、重新分发，远比网页改完即生效繁琐。

### 3. 分发与信任：体验瑕疵，不是门槛

* Windows 下未签名的 EXE 直接运行**不会出现任何系统警告**（轻壳产物亦然）——构建分发本就没有签名门槛，代码签名证书只是可选的信任增强，不是分发前提（这与 Mac 强制签名公证完全不同）。
* Web 方向（HTTPS）自带信任背书，用户零门槛打开。
* **唯一要留意的**：新编译的未签名程序可能被杀毒软件误报（Defender 或其他杀软），属常见现象；加白名单或购买证书即可缓解。

> **本项目对应**：模板产物未签名即可正常构建、分发与安装，运行不会触发任何系统警告；
> 唯一可能遇到的是杀毒软件对新程序的误报，加白名单或按需购买证书即可缓解
> （详见[使用说明.md](./使用说明.md)「云构建」章常见问题）。

**小结**：三条边界划下来，轻壳的适用面只剩一种项目——**前端逻辑足够简单（无后端）、但必须呈现为“桌面软件”形态**。绝大多数项目不在此列，所以“鸡肋”的观感是真实的，不必辩解。

## 二、 窄场景里的不可替代性：什么时候非它不可

用最直白的话说：**你不想忍受网页的质感，想要一个随时双击就能打开、看起来就是个软件的桌面应用。**
这一条就是轻壳的全部出发点。展开成需求，是下面三点——前两点一旦存在，Web 方向**完全无法满足**，轻壳是比较适合的一个选择；第三点的源码门槛只是附带属性。

### 1. 必须“安装”而非“访问”

* **Web 方向**：用户是在“访问”一个地址；**轻壳方向**：用户是在“使用”一个软件。
* 独立的 EXE、开始菜单入口、控制面板卸载项——这种“安装”的过程，对非技术用户就是专业度的体现。
* **典型场景**：给客户交付产品、软件商店上架、企业内网统一分发——以及更朴素的：**自己日常使用的工具，不想每次打开浏览器、翻收藏夹，而是桌面/任务栏一个图标双击即用**。这类场景要求的就是“软件形态”，网页给不了。

> **本项目落地**：自带安装/卸载向导（`installer/` 子包）——欢迎 → 路径选择 → 选项 → 进度 → 完成，
> 控制面板“卸载”一键走卸载向导，行为对齐 NSIS 而 UI 与应用同风格；单文件分发，双击即进安装流程。

### 2. 必须深度介入系统

* 无边框/自绘标题栏：构建独特设计语言（磨砂玻璃、异形窗口、去线留白）的唯一路径。
* 系统级交互：托盘常驻、开机自启、全局快捷键、进程单例——纯 Web 技术触及不到的领域。

> **本项目落地**（深度集成但尽量零配置）：
> * **自动边框判定**：页面带自绘标题栏（`data-tauri-drag-region`）则无边框窗口，否则自动切回系统原生标题栏，判定与切换发生在窗口显示前、无视觉跳变；
> * **系统托盘**：关闭窗口最小化到托盘（设置页可关）、托盘左键还原主窗口、右键弹出与应用同风格的自绘菜单（透明 Webview 小窗渲染，非原生菜单）；并拦截原生标题栏的关闭事件，防止主窗口销毁后托盘无法还原的僵尸进程；
> * **窗口显示接管**：页面加载完成且边框判定后才显示窗口，另有 2 秒超时兜底，杜绝白屏闪烁，页面无需调用 `show`。

### 3. 附带属性：聊胜于无的源码门槛

* 网页源码天然公开；轻壳把资源编译进二进制，确实挡住了普通用户——但仅此而已：稍微有点技术能力的人，用现成工具即可从二进制中提取出 HTML/JS/CSS，谈不上真正的保护。
* **结论**：源码门槛只是轻壳的附带属性，不应作为选择它的理由；真有保护需求，要靠后端逻辑、混淆与加密等手段，而不是指望这个壳。

**小结**：真正构成“不可替代”的是前两点——**都是“存在形态”需求，而非“功能”需求**；第三点的源码门槛只是附带属性，聊胜于无。要功能，网页够了；要形态，才轮到轻壳。这就是它“窄而不可替代”的原因。

## 三、 决策指南：四把尺子，多数答案指向 Web

不要用“好坏”评判，用“匹配度”决定。**注意：只有四项的答案全部指向轻壳，才值得选它；任何一项指向 Web，都请先认真考虑 Web 方向。**

1. **你的核心逻辑是否依赖非 Rust 的后端（如 Python/Java）？**
   * **是** → 轻壳**不匹配**。请考虑 Electron（兼容 Node）或原生开发。
2. **你的产品是否极度依赖“桌面级”UI 表现或系统深度交互（如无边框、托盘）？**
   * **否** → 建议 **Web 方向**（PWA 或直接分发 HTML），配置成本最低。
   * **是** → 轻壳方向匹配，这是实现该形态的必经之路。
3. **你的分发场景是否要求“安装包”形态（客户交付、商店上架、内网分发）？**
   * **否** → **Web 方向**更灵活，更新即时生效。
   * **是** → 轻壳方向符合软件分发规范，但每次改版都要重新构建分发。
4. **你是否介意新程序可能被杀毒软件误报（未签名时更常见）？**
   * **介意** → 需自购代码签名证书，或考虑 **Web 方向**（HTTPS 自带信任背书）。
   * **不介意** → 可以使用轻壳——未签名直接运行不会触发系统警告，分发本无门槛。

## 四、 本项目（轻壳模板）的定位对照

先说初衷：轻壳的定位，是让“套壳”这件事不再需要操心——当你决定把一个 HTML 打包成桌面应用，
窗口、标题栏、托盘、安装器这些壳的部分都已备好，把 HTML 放进去即可构建、安装、分发；想要界面，
壳内还备有一整套「去线留白」组件（Toast / Modal / Tab / 右键菜单等，见 [components/](../components/)）
可按需选用。这个项目源于一次真实的交付：为完成一个工具订单，当时四处寻找套壳方案，
却发现没有“套上就能立即搭建应用”的壳，总要捣鼓很久的环境与配置，于是索性自己做了这一个。

本项目是这一架构方向的一个**最小可运行样本**。用上面四把尺子对照：

| 决策问题 | 本模板的回答 |
|---|---|
| 是否依赖非 Rust 后端？ | 否。Rust 层几乎零逻辑，业务全部在前端 HTML |
| 是否依赖桌面级 UI / 系统交互？ | 是。自动边框判定、托盘、自绘菜单、安装向导均为“存在形态”能力 |
| 是否要求安装包形态？ | 是。自带安装/卸载向导，单文件分发，控制面板集成 |
| 是否接受未签名运行？ | 接受。产物默认未签名，直接运行无系统警告，证书为可选的信任增强 |

因此：**如果你恰好四项全中，本模板就是轻壳方向的开箱即用底座**——把 `dist/index.html` 换成你的页面即可，
无需保留示例页任何代码，标题栏与窗口显示由壳自动适配。反之，若任一问题的回答在 Web 一侧，请回到决策指南重新权衡——
**本模板并不打算把“其实只需要一个网页”的项目变成桌面软件。**

### 最简单的玩法：只要一个 HTML

轻壳最直接的使用方式，把“套壳”这件事压缩到三步：

1. **准备一个网页**——只要一个 `index.html`（单文件，资源尽量内联）；
2. **替换示例页**——把本仓库 fork 到你的 GitHub，网页端打开 `dist/index.html`，用你的代码整体替换示例页面，无需保留示例页任何代码，标题栏与窗口显示由壳自动适配；
3. **云端重新构建**——在仓库的 Actions 页面手动运行「构建安装包」，或发一个 `v*` 标签的 Release；构建完成后从 Artifact（或 Release 附件）下载安装包，双击即进入安装向导。

全程不需要在本地安装 Rust / Node，也不需要跑任何构建命令——你要做的只是把 HTML 放进去。
标题栏自适应、托盘、安装向导、组件库这些“壳的部分”都由项目代劳，这正是开头“套上就能立即搭建应用”的初衷。
所以这个场景虽窄，搭建成本却已经被压得很低：**想要一个桌面端的简单应用，这可能是最快的路径。**

### 更进一步：开源基础上的扩展

本项目以木兰宽松许可证开源，全部代码都在仓库里，可以 fork 后基于这个基础自行完善——做更复杂的应用也是可以的：
加 Rust 命令、接入后端服务、扩展前端逻辑，壳不会拦你。

但边界要认清：轻壳保证的是“套壳”这件事的简单可靠——标题栏、托盘、安装向导等“形态”部分开箱即用，
它并不为复杂应用设计（Rust 层几乎零逻辑、前端单 HTML）。一旦扩展成复杂应用，**可靠性与性能需要你自己负责**，
架构的稳健性不在本模板的保障范围内——这也呼应了第一章“带后端不适用”的边界：那指开箱即用，不指 fork 后的自行扩展。

## 五、 结论

不回避“鸡肋”的评价：**对大多数项目而言，轻壳就是鸡肋**——场景窄，更新换代也不如网页即时，网页能做的事它做得更费劲。但场景窄不等于成本高：有了上一章的三步玩法，**搭建一个桌面端简单应用的成本已经很低**。
它并非 Web 开发的进阶版，而是一条**完全不同的技术分支**：

* **Web 方向（PWA/裸 HTML）**：追求**流动与开放**。代码即应用，随时更新，零门槛分发。
* **轻壳方向（Tauri）**：追求**固化与封闭**。应用即资产，强调桌面主权，强交互控制。

两者的取舍标准从来不是“哪个更好”，而是“你要功能还是形态”。**当你的需求是“看起来像软件、管起来像软件”的容器时——交付要安装包、界面要无边框、系统要有托盘——轻壳不可替代；当你只是想快速交付一个能用的工具时，一个网页就够了，别用轻壳。** 本项目「轻壳」正是这样一只容器：它不提供功能，它只提供软件的形态，而这只对形态有刚需的人有用。
